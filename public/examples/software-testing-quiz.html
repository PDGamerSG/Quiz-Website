Corrections and clarifications from the study material

The quiz uses the PDFs as study sources, while correcting conflicting or inaccurate claims. Page numbers below refer to PDF pages, including handwritten pages.

  • Condition coverage (PDF 5, pp. 28-33): four example tests are not always the minimum. If every operand is evaluated, TTT and FFF cover both values of all three conditions. Short-circuit execution can skip conditions, so supplied values alone do not establish runtime coverage.
  • Graph matrices (PDF 5, pp. 38-43): a binary entry can hide parallel edges. Cyclomatic complexity must use distinct edge counts and the correct graph assumptions; the shortcut based on nonblank rows is not universally valid.
  • Mutation testing (PDF 5, pp. 45, 51, 61): a survivor may be equivalent or expose weak tests. Mutation testing is one way to assess test strength. This quiz explicitly excludes known equivalent mutants in adjusted-score questions; tool reports may differ.
  • Data flow (PDF 5, pp. 67-71): if(z>10) reads z, not x. With fixed assignments x=5 and y=10, the false branch is unreachable. Values 3 and 5 require changing the program to accept controllable inputs.
  • Loop testing (PDF 5, pp. 87-91): testing can reveal loop defects. It does not itself limit iterations or guarantee termination. Nested and sequential loops are structured; their combination alone is not an unstructured loop. The shown code does not reject rows=0 or enforce a maximum of 10.
  • Static testing and reviews (PDF 4, pp. 2-11, 29-46): static analysis is also static testing. Technical reviews focus on technical issues, rather than being defined by management attendance. Dynamic testing followed by diagnosis can also locate a defect.
  • Example fixes (PDF 4, pp. 12-13): adding a semicolon and braces does not add missing age validation. Source snippets and defect severity labels should be assessed in their actual context.
  • Test levels and types (PDF 4, pp. 76, 87-106): system testing is a level, while black-box testing is a technique category. Levels may overlap in iterative development. Acceptance decisions and release criteria depend on the agreed process.
  • Failed tests (PDF 4, p. 85): investigate a result mismatch before attributing it to a software defect. Test expectations, data and environment can also be wrong.
